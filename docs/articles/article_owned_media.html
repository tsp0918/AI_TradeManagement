CHAPTER 01

そもそも、なぜ「外為法 AI」を作ろうと思ったのか

このプロジェクトの起点は、ある製造業クライアントとの何気ない会話でした。 「新しく開発した精密センサーを海外の大学の研究室に納品したいのだが、 輸出許可がいるかどうかわからなくて困っている」という相談です。

最初は「ちゃんとした専門家に聞けばすぐわかるはず」と思っていました。 ところが調べると、専門コンサルに頼むと数週間待って数十万円の費用がかかる。 社内で判断できる人材は大手企業にしかいない。中堅・中小は基本的に 「やってみて指摘されたら直す」という綱渡りをしている実態がわかってきたんです。

📖
外為法（外国為替及び外国貿易法）の基礎知識： 輸出する際に経済産業大臣の許可が必要な「規制品目」を定めた法律。 武器はもちろん、半導体製造装置・化学品・暗号技術・工作機械など広範囲に及ぶ。 対象品目は「外為令別表」に掲載されており、各項目に技術的パラメータ（閾値）が細かく規定されている。 違反した場合、個人は最大で懲役 5 年・罰金 100 万円、法人は 1 億円の罰金となる。

しかし最大の問題は「知識が組織に蓄積されない」構造でした。 毎回、外部専門家に「OK」「NG」だけ聞いて、なぜそうなのかを学ばない。 同じような製品が出るたびに、また一から始まる。 これはシステムで解決できる問題だと確信しました。

最大の問題は「知識が組織に蓄積されない」こと。毎回 OK/NG だけ聞いて、なぜかを学ばない——これはシステムで解決できる。

CHAPTER 02

最初の壁：「LLM に聞けばいい」という幻想

最初に試みたのは、当然のように「最新の LLM に聞いてみる」でした。 GPT-4 や Claude に「この技術仕様は外為法何項に該当しますか？」と聞いてみると…… なるほど、もっともらしい回答が返ってきます。 しかし専門家にチェックを依頼すると、かなりの頻度で間違っていたのです。

LLM が規制判定に使えない理由

✕
ハルシネーション：存在しない条文番号を引用する。「外為令別表第1の7項(3)号イ」と言いながら、実際の文言と全く異なる内容を説明する。
✕
知識カットオフ問題：外為法は頻繁に改正される。トレーニングデータに含まれない最新の改正内容は知らない。コンプライアンス判断で「古い法律ベースで OK」は最悪のパターン。
✕
根拠の非透明性：「この製品は規制対象ではありません」と言われても、なぜそう判断したかがわからない。担当者がダブルチェックできない。
✕
閾値判定の曖昧さ：「動作周波数が 3GHz 超の装置は規制対象」のような数値的閾値判定で、文脈によって異なる答えを返す。再現性がない。

これらの問題を分析して気づいたのが、根本的なアーキテクチャの誤りでした。 LLM は「知識を持っている」ように見えて、実際には「確率的に最もらしい文字列を生成している」。 コンプライアンスの領域で「もっともらしい」は「確実に正しい」ではない。

💡
アーキテクチャの根本的問い： LLM に「知識を持たせる」のではなく、「知識は別に持ち、LLM は対話と自然言語処理に専念させる」 設計にできないか？ この問いが NeuroSymbolic アーキテクチャへの転換点になった。
CHAPTER 03

NeuroSymbolic という答え：Neural + Symbolic の統合

「規制知識はコードで明示的に持ち、LLM は対話のみを担当する」—— この設計原則を固めてから、アーキテクチャが一気に明確になりました。

Symbolic 側：オントロジーの構築

外為令別表の各項目を、人間が読める JSON 形式で形式化します。 これがHanteiKubanbang（判定項番）オントロジーです。

platform_core/ontology/seed/hantei_kubanbang.json（抜粋） 
{
  "domain_id": "FEFTA::7::weapon::1-7",
  "source_type": "FEFTA",
  "article_no": "1-7",
  "title": "電子機器・センサー（7項）",
  "thresholds": [
    {
      "threshold_type": "numeric",
      "attr_key": "operating_frequency_ghz",
      "label": "動作周波数",
      "unit": "GHz",
      "operator": "gte",
      "controlled_value": 3.0,
      "description": "3GHz以上の電子機器は規制対象"
    }
  ]
}

このシードデータは現在 29 項目（外為法 17 + ECCN 12）、 40 種類以上の属性キーを持つまでに成長しています。 重要なのは、これがコードとは独立した知識データであること。 法改正があれば JSON を更新するだけで、エンジン全体は変わりません。

Neural 側：FAISS + E5-large の組み合わせ

規制知識は形式化できた。次の問題は「どの規制項目が、この品目に関係するか」を 高速に検索することです。29 項目ならば全件確認も可能ですが、 将来的なスケールを考えてベクトル検索を採用しました。

エンベッディングモデルには intfloat/e5-large-v2 を選択しました。 理由は日本語・英語の混在テキストへの対応力と、技術文書での精度。 外為法の規制文は日本語、ECCN は英語ですが、実務の品目説明は両方が混在します。 この多言語性が決め手でした。

CHAPTER 04

FAISS 三層設計の試行錯誤

当初は単一の FAISS インデックスで始めました。 「品目の申告用途テキスト」を直接ベクトル化して、規制項目と照合するシンプルな設計です。 しかし実際に試してみると、精度が安定しなかった。

なぜ単一インデックスではダメだったか

✕
申告用途のバイアス問題：企業が申告する「用途」はしばしば過小申告される。「農業用ドローン向けセンサー」と書かれていても、実際の技術仕様は軍事転用が可能なケースがある。申告文面だけを見ていると見落とす。
✕
HS コードのミスマッチ：同じ品目でも、HS コード（関税分類）の照合では別のベクトル空間が必要。技術用途テキストと HS 分類テキストは意味空間が異なる。

この問題を解決するために、三層インデックス設計を採用しました。

DIAGRAM — FAISS 三層インデックス構造と Two-List 判定
✓
Layer B（拡張用途）の効果：「農業用ドローンセンサー」を申告した製品が、拡張用途インデックスで「慣性航法・誘導制御」にマッチし、7 項候補として浮上——申告文面だけでは発見できなかったリスクを検出。
✓
intersection 判定の威力：申告用途・拡張用途の両方で規制項目に一致するケース（intersection）を最高優先度とすることで、担当者のレビュー順序が明確になった。「どこから先に見ればいいか」問題が解決した。
CHAPTER 05

「required − known = missing」対話パターンの誕生

FAISS で候補項目を絞り込めるようになりました。次の問題は「候補を判定するための情報が不足している」ことです。 たとえば 外為法 7 項に「3GHz 以上の電子機器」という閾値がある場合、 FAISS が候補を挙げても、品目の実際の動作周波数がわからなければ判定できない。

情報不足を「会話」で補う

ここで採用したのが、HanteiAgent の対話パターンです。 概念は極めてシンプルな数式で表せます：

core concept — HanteiAgent 判定ロジック 
# 候補項目 D が判定に必要とする属性
required = ontology.get_required_attrs(candidate_domain_id)

# ユーザーが既に提供済みの属性（TransactionContext に蓄積）
known = context.get_known_attrs()

# 不足している属性 = 質問すべき内容
missing = required - known

if missing:
    # Claude が自然言語で担当者に質問
    question = llm_bridge.generate_question(missing[0], context)
    return AgentResponse(message=question, waiting_for_attr=missing[0].attr_key)
else:
    # 情報が揃ったら最終判定
    judgment = ontology.evaluate(candidate_domain_id, known)
    return AgentResponse(judgment=judgment, status="ready_for_judgment")

この設計の美しさは、LLM が「何を聞くか」は決めず、「どう聞くか」だけを担当する点です。 「何を聞くべきか」はオントロジーが定義する（required）。 LLM は missing 情報を人間が答えやすい自然言語の質問に変換するだけ。 これによりハルシネーションのリスクを最小化できました。

セッション永続化の必要性

対話型エージェントを作ってすぐに気づいたのが「中断問題」です。 担当者が途中でブラウザを閉じたら？ 翌日に続きを再開したい場合は？

platform_core/ontology/db/schema.py — AgentSessionORM（抜粋） 
class AgentSessionORM(PlatformBase):
    __tablename__ = "plat_agent_session"

    session_id: Mapped[str]  # UUID、外部から参照するキー

    # TransactionContext の JSON スナップショット
    # dialogue_history も含まれる → 対話の完全な再現が可能
    context_snapshot: Mapped[Optional[dict]] = mapped_column(JSON)

    # 候補項番（カンマ区切り）
    # FAISS 検索結果を永続化 → 再起動後も同じ候補から再開
    candidate_domain_ids: Mapped[Optional[str]] = mapped_column(Text)

    status: Mapped[str]  # active | ready_for_judgment | judged | abandoned
    turn_count: Mapped[int]

セッション復元の際に一番悩んだのが「最後に聞いていた質問の再現」です。 _last_missing_attr を DB に保存するカラムを追加するか、 それとも dialogue_history から導出できるかを検討しました。 最終的に「dialogue_history の最後のターンで answer is None のものの attr_key を使う」 という方法で解決。専用カラムを増やさずにすっきり復元できます。

🎓
学んだこと： DB スキーマはシンプルに保ち、「データから導出できる情報は計算で求める」原則を徹底すること。 復元ロジックをコードに閉じ込めることで、DB の肥大化を防ぎ、 スキーマ変更コストを最小化できた。
CHAPTER 06

マルチモジュール化の判断と苦労

NeuroSymbolic エンジンが動くようになってから、次の設計判断が訪れました。 「全機能を一つのアプリに入れるか、複数のモジュールに分割するか」です。

結論はマイクロサービス的マルチモジュール設計でした。 理由は「ユーザーが使う文脈」が根本的に異なるから。 輸出規制を判定する担当者と、特許調査をしている研究者と、 R&D プロジェクトのリスク評価を行う管理者では、ワークフローが全く異なる。

モジュール間通信で学んだこと

✕
最初の失敗：同期 HTTP 呼び出し in async — FastAPI の async ルートから requests.get() を呼んでいた。イベントループをブロックし、高負荷時に全体が詰まる問題。
✓
解決：httpx + asyncio.to_thread — モジュール間通信は httpx.AsyncClient、BigQuery など同期 SDK は asyncio.to_thread() でオフロード。一貫した非同期設計を徹底。
✕
BigQuery のシングルトン問題 — リクエストごとに BigQueryService を初期化していた。認証・コネクション確立コストが毎回発生し、レスポンスタイムが不安定。
✓
解決：モジュールレベルシングルトン — _bq_service: Optional[BigQueryService] = None でモジュールスコープのシングルトン。get_bigquery_service() で遅延初期化。起動時のオーバーヘッドも削減。
CHAPTER 07

本番に向けた品質と運用の整備

WAL（Write-Ahead Logging）の徹底

SQLite モジュールでは WAL モードを全面採用しました。 PRAGMA journal_mode=WAL + synchronous=NORMAL + busy_timeout=30000 ms。 複数プロセスからの同時書き込みに対する排他ロック待ちを最小化し、 FastAPI の非同期環境での安定性を確保しています。

エグゼクティブサマリーの自動生成

PDF レポートにエグゼクティブサマリーを追加した際、 「どのロジックでリスクレベルを自動判定するか」を慎重に設計しました。

modules/ai_validation/app/services/export_report.py — _build_executive_summary() 
def _build_executive_summary(two_lists, tx):
    c = two_lists.get("counts", {})
    intersection = c.get("intersection", 0)
    core_only    = c.get("core_only", 0)

    if intersection > 0:
        risk_level = "HIGH"     # 両方の観点で規制一致 → 許可確認必須
    elif core_only > 0:
        risk_level = "MEDIUM"  # 申告用途で規制一致 → 精査推奨
    else:
        risk_level = "LOW"     # 一致なし → ファイリングして保管

    # ... 推奨アクション・上位規制項目チップを生成 ...
    return {
        "risk_level": risk_level,
        "recommended_actions": [...],
        "top_items": [...],
    }

ダッシュボードに NeuroSymbolic 統計を組み込む

platform-core のダッシュボードには、既存の案件カードに加えて HanteiAgent のセッション統計（進行中・判定待ち・完了数）を リアルタイムで表示するメトリクスパネルを追加しました。 「システムが実際にどれだけ使われているか」を一目で把握できる設計です。

🎓
大切にしている設計原則： 「コードで解決できることは、コードで解決する。DB スキーマを太らせない」。 シンプルさが保守性の源泉。over-engineering は技術的負債の積み上げ。 ミニマルな実装から始めて、本当に必要になってから拡張する。

正直に言う「まだ足りないこと」

このシステムが解決しようとしている問題はまだ道半ばです。正直に言います。

オントロジーのカバレッジ： 現在 29 項目ですが、外為令別表の全項目をカバーするには 100 項目以上が必要です。 特に生物・化学兵器関連（1 項）、核関連（2 項）は技術的に複雑で、 属性設計に専門家の協力が不可欠です。

FAISS の精度継続評価： 実際の規制判定ケースでの適合率・再現率を継続測定する仕組みが必要です。 「なんとなく精度が高そう」ではなく、「このインデックス更新でどう変わったか」を 定量的に追跡できるテストスイートを整備する計画があります。

法的リスクの整理： AI が「規制対象ではない」と判定し、それを信じて輸出した結果、違反が発覚した場合、 責任はどこにあるのか。これは技術的な問題ではなく法的・倫理的な問題ですが、 真正面から向き合う必要があります。現時点では「判断支援ツール・最終判断は人間が行う」 というポジションを明確にしています。

「完璧なシステムは存在しない。だからこそ、どこまで何ができて、何ができないかを明示する設計が大切だ」
